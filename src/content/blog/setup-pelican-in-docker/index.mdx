Over time, the [official documentation for running Pelican in Docker](https://docs.pelican.dev/panel/installation/docker/) has evolved and become simpler, and the maintainers always publish an official Docker image for each release that we can use instead of building the images ourselves.

<Banner type={BannerType.Info}>
  **Updated October 2026:** The official Pelican images have moved from
  `ghcr.io/pelican-dev/*` to `ghcr.io/pelican/panel:latest` and
  `ghcr.io/pelican/wings:latest`. The examples below use the new image names. If
  you already followed this guide, update the `image:` lines in your
  `docker-compose.yml`, then run `docker compose pull && docker compose up -d`.
</Banner>

## Assumptions

In order to keep this guide relatively concise, we need to assume a few things about your setup.

1. You're running a Debian-based Linux distro (Ubuntu) with [Docker installed](how-to-install-docker) and apt packages updated
2. You have [familiarity with Docker](./first-docker-containers) and Docker Compose
3. You own a Domain name and have your reverse proxy set up to hand out wildcard SSL certificates. We will use Nginx Proxy Manager (NPM) in this guide, but similar concepts apply to other reverse proxies. It is best if the reverse proxy is running on a different machine or VM on your network than where Pelican will be running.

## Getting Started

The first part of this guide will be setting up and configuring the Pelican Panel web interface. The panel is where you will manage your game servers, and it also serves as the central hub for your Wings nodes to connect to. The panel will be running in a Docker container, and we will use Docker Compose to manage the stack. The second part of the guide will be setting up a Wings node, which is the service that actually runs your game servers. Wings will also be running in a Docker container on the same machine as the panel, but it could also be run on a different machine if you wanted to distribute your nodes across multiple servers.

---

1. SSH into your debian-based linux machine on which to install Pelican
2. Make a pelican directory in home folder with `mkdir ~/pelican && cd ~/pelican`
3. Create a Docker Compose file in the pelican directory with `touch ~/pelican/docker-compose.yml` and paste the following contents, replacing `<YOUR_EMAIL_HERE>` with your email address, `<YOUR_NPM_IP_ADDRESS>` (e.g. 192.168.1.100) with the IP address of your reverse proxy, and `<YOUR_HTTPS_PANEL_URL_HERE>` with the HTTPS URL of your panel (e.g., https://pelican.local.example.com).

```yaml title="~/pelican/docker-compose.yml" {18-19,21}
services:
  panel:
    image: ghcr.io/pelican/panel:latest
    container_name: pelican_panel
    restart: always
    networks:
      - default
    ports:
      - "80:80"
    extra_hosts:
      - "host.docker.internal:host-gateway"
    volumes:
      - pelican-data:/pelican-data
      - pelican-logs:/var/www/html/storage/logs
      - ./Caddyfile:/etc/caddy/Caddyfile
    environment:
      XDG_DATA_HOME: /pelican-data
      APP_URL: "<YOUR_HTTPS_PANEL_URL_HERE>"
      ADMIN_EMAIL: "<YOUR_EMAIL_HERE>"
      BEHIND_PROXY: "true"
      TRUSTED_PROXIES: "<YOUR_NPM_IP_ADDRESS>"

volumes:
  pelican-data:
  pelican-logs:

networks:
  default:
    ipam:
      config:
        - subnet: 172.20.0.0/16
```

---

Then create a Caddyfile in the same directory `~/pelican/Caddyfile` (no file extension) with the following contents, replacing `<YOUR_NPM_IP_ADDRESS>` with the IP address of your reverse proxy. The Caddyfile is used to configure the web server that serves the Pelican panel. We need to tell Caddy to trust our reverse proxy so that it can properly handle requests and forward them to the panel

```caddyfile title="~/pelican/Caddyfile" {4}
{
  admin off
  servers {
    trusted_proxies static <YOUR_NPM_IP_ADDRESS>
  }
}

:80 {
  root * /var/www/html/public
  encode gzip

  php_fastcgi 127.0.0.1:9000 {
    env PHP_VALUE "upload_max_filesize = 512M
      post_max_size = 512M"
  }
  file_server
}
```

---

## Accessing the Panel

Start the Docker Compose stack with `docker compose up -d`. Note: You may need to prefix your docker commands with `sudo` if your user is not in the docker group

View the logs with `docker logs -f pelican_panel` to check for errors at any point if you're having trouble.

Since we are using NPM as a reverse proxy to access our panel at a custom domain, we need to add a "Proxy Host" entry in NPM pointing at our server. As seen in the compose file, we are exposing ports 80 and 443 for HTTP and HTTPS traffic, respectively.

In NPM, add a new Proxy Host with the following settings:

- Domain Names: `<YOUR_HTTPS_PANEL_URL_HERE>` (same as the APP_URL in the compose file, without the https:// prefix. e.g. `pelican.local.example.com`)
- Scheme: http
- Forward Hostname/IP: 192.168.1.XXX (IP of your Pelican server)
- Forward Port: 80
- Websockets Support: Enabled
- Block common exploits: Enabled
- SSL Tab -> Select your certificate for the domain and check "Force SSL" and "HTTP/2 Support"

## Setting up a Wings Node

The [official Pelican Wings documentation](https://pelican.dev/docs/wings/install) doesn't have instructions for running Wings in Docker, but it's actually very simple to set up. We will modify our Docker Compose file to add a new service for Wings.

Update your `docker-compose.yml` file to look like this, replacing `<YOUR_EMAIL_HERE>` with the same email address from the Panel, `<YOUR_NPM_IP_ADDRESS>` with the IP address of your Reverse Proxy, and `<YOUR_HTTPS_PANEL_URL_HERE>` with the HTTPS URL of your panel (e.g., https://pelican.local.example.com).

<Banner type={BannerType.Warning}>
  **Remember!** _Indentation matters_ in YAML files, so make sure to copy and
  paste the code correctly. The `panel` service should be unchanged, and the
  `wings` service should be added below it. The `networks` section should also
  be updated to include a new network for Wings.
</Banner>

```yaml title="~/pelican/docker-compose.yml" ins={23-46,58-65}
services:
  panel:
    image: ghcr.io/pelican/panel:latest
    container_name: pelican_panel
    restart: always
    networks:
      - default
    ports:
      - "80:80"
    extra_hosts:
      - "host.docker.internal:host-gateway"
    volumes:
      - pelican-data:/pelican-data
      - pelican-logs:/var/www/html/storage/logs
      - ./Caddyfile:/etc/caddy/Caddyfile
    environment:
      XDG_DATA_HOME: /pelican-data
      APP_URL: "<YOUR_HTTPS_PANEL_URL_HERE>"
      ADMIN_EMAIL: "<YOUR_EMAIL_HERE>"
      BEHIND_PROXY: "true"
      TRUSTED_PROXIES: "<YOUR_NPM_IP_ADDRESS>"

  wings:
    image: ghcr.io/pelican/wings:latest
    container_name: pelican_wings
    restart: unless-stopped
    networks:
      - wings0
    ports:
      - "2022:2022"
      - "8080:8080"
    environment:
      TZ: "UTC"
      WINGS_UID: 998
      WINGS_GID: 998
      WINGS_USERNAME: pelican
    volumes:
      - "/var/run/docker.sock:/var/run/docker.sock"
      - "/var/lib/docker/containers/:/var/lib/docker/containers/"
      - "/etc/pelican/:/etc/pelican/"
      - "/var/lib/pelican/:/var/lib/pelican/"
      - "/var/log/pelican/:/var/log/pelican/"
      - "/tmp/pelican/:/tmp/pelican/"
      - "/etc/ssl/certs:/etc/ssl/certs:ro"

volumes:
  pelican-data:
  pelican-logs:

networks:
  default:
    ipam:
      config:
        - subnet: 172.20.0.0/16

  wings0:
    name: wings0
    driver: bridge
    ipam:
      config:
        - subnet: 172.21.0.0/16
    driver_opts:
      com.docker.network.bridge.name: wings0
```

## Connecting to your Server

There are a few situations where you might want to connect to your server, and each has some details specific to it.

### 1. Connecting from LAN using IP address

This is already working! You can connect to your server on your LAN (home network) using the Pelican server's IP address and the port you allocated (e.g., `192.168.1.50:25565`).

<Image
  src={minecraft_lan_ip_connection}
  alt="Minecraft LAN IP Connection Screen"
/>

### 2. Connecting from WAN using IP address

This requires forwarding the server port on your router (Google your router's model for detailed instructions) from the WAN to your Pelican server address.

For a general overview, log into your router's admin panel (e.g. http://192.168.1.1) and go to the Port Forwarding section (might be under Advanced settings).

Then you will need to add an entry here along the lines of:
"Forward traffic from WAN on port `25565` (or whichever port you want) to my server on LAN IP `192.168.1.50` on port `25565`".

Save that, then you will need to find your WAN public IP address ([whatismyip.com](https://www.whatismyip.com/) works great for this) and give it to whomever you want to connect to your server. They will open Minecraft and connect to `XX.XX.XX.XX:25565` where the `XX...` is replaced by your public IP.

Note that you might not be able to connect to your server from that same address while on your LAN. Many routers don't support **NAT loopback** (also called NAT hairpinning), which is when a request from inside your network goes out to your own public IP and back in. Instead, use the LAN IP address from situation #1 above.

<Banner type={BannerType.Error}>
  Your public IP address is **sensitive information** and can be dangerous in the hands of the wrong people.

They can DDoS attack you, exploit vulnerable services on open ports on your network, use GeoLocation to find the city you live in, connect to your server (use a whitelist to avoid this), and more.

It is important that you understand the risks before forwarding ports and sharing your public WAN IP.

</Banner>

### 3. Connecting from LAN using FQDN

This section is about connecting to your server with a Fully Qualified Domain Name (FQDN) like `minecraft.local.example.com` instead of an IP address.

#### How DNS resolution works

When you type an FQDN into Minecraft, your PC first has to turn it into an IP address. It asks your router (or Pi-hole/AdGuard Home, if your router uses one as its DNS server). The router checks its own local DNS entries first. It only finds a match if someone has added an "A" or "CNAME" record there. If there's no match, it asks upstream DNS servers like Google, Cloudflare or Quad9, which know every public FQDN on the internet. That's how `www.google.com` gets resolved to one of Google's servers.

So to use an FQDN on your LAN, we add a local DNS record that points the name at a machine on your network.

#### Adding the DNS record

Like the port forwarding section above, you'll probably need to Google your router's model for exact steps. In general, log into your router's admin panel (e.g. http://192.168.1.1) and find the DNS Server section (it might be under Advanced settings).

Add an entry along the lines of:
"Domain Name ('A' Record): `minecraft.local.example.com` -> LAN IP: `192.168.1.50` (Pelican server)"

That's it! Connect in Minecraft with `minecraft.local.example.com:25565`. The DNS record handles the name and the port goes straight to Wings, so no proxy is involved.

<Image
  src={minecraft_lan_fqdn_connection}
  alt="Minecraft LAN FQDN Connection"
/>

<Collapsible title="Alternative: Reusing an FQDN pointed to NPM">

If you already have a DNS record (wildcard or individual) that points to Nginx Proxy Manager, the name resolves to NPM's IP rather than Pelican's. In that case, NPM has to pass the game traffic along to Pelican. Normal Proxy Hosts in NPM only handle HTTP, while Minecraft uses raw TCP (and UDP for voice chat), so we need a **Stream**.

In NPM, create a new Stream under "Hosts -> Streams" and enter the following details:

| Field          | Value        | Note                             |
| -------------- | ------------ | -------------------------------- |
| Incoming Port  | 25565        | Whichever port your server is on |
| Forward Host   | 192.168.1.50 | Pelican server IP                |
| Forward Port   | 25565        | Same as above                    |
| TCP Forwarding | Yes          |                                  |
| UDP Forwarding | Yes          | Used for MC voice chat           |

<Image src={npm_stream} alt="NPM Stream" />

Repeat this for every port allocation you use in Pelican. NPM doesn't support port ranges yet. The underlying Nginx can do it, but there's an open [GitHub issue](https://github.com/NginxProxyManager/nginx-proxy-manager/issues/1969) tracking it in NPM.

If NPM runs in Docker, you'll also need to map each port onto the container:

```yaml {5,6}
ports:
  - 80:80 # Existing NPM port
  - 81:81 # Existing NPM port
  - 443:443 # Existing NPM port
  - 25559:25559 # Game server port
  - 25560-25570:25560-25570 # Game server port ranges
```

Your DNS record should point to NPM's IP (e.g. `minecraft.local.example.com -> 192.168.1.100`), not Pelican's.

If you use a wildcard record like `*.local.example.com`, keep in mind that **any** subdomain will reach your server on that port. For example, `scoobydoo.local.example.com:25565` works too. If you don't want that, create a separate record for each subdomain instead of a wildcard.

</Collapsible>

### 4. Connecting from WAN using FQDN

This is the final method I will cover and it's the holy grail of what I was chasing when trying to create a Minecraft server when I was 13. All the public servers I used to play had super clean URLs like `minecraft.example.com` and it seemed like magic to me. Fast forward to the late 2020s and we've cracked the code!

The process here is pretty simple and combines the LAN FQDN method and WAN IP methods from earlier. Here are the steps:

1. Create a DNS ("A") record in your cloud _domain provider_ (the place you bought example.com from) and point it to your WAN (public) IP address
2. Forward your server ports on your home router to your Pelican server (e.g. WAN 25565 -> LAN 192.168.1.50:25565)

This is the same idea as the [LAN DNS record](#adding-the-dns-record) from section 3, except the record lives at your public domain provider and points to your public IP.

And you're done! Similar to the WAN IP method, you might not be able to connect to this address from a device on your LAN. Many routers don't support **NAT loopback** (also called NAT hairpinning or NAT reflection), which is when a request from inside your network goes out to your own public IP and back in. You can work around this with a local DNS override (the same [LAN DNS record](#adding-the-dns-record) from section 3), so the same FQDN resolves to `192.168.1.50` at home and to your public IP everywhere else.

## Updating Pelican

Since we're using the official images, updating Pelican is just a matter of pulling the newest images and recreating the containers. There's no need to clone repositories or build anything ourselves.

Panel and Wings releases are usually published around the same time, and running the latest version of both is recommended. You can follow new releases here: [Panel](https://github.com/pelican-dev/panel/releases), [Wings](https://github.com/pelican-dev/wings/releases).

### 1. Back up your data

Before updating, it's a good idea to back up your data and skim the release notes for any breaking changes. If something goes wrong, a backup lets you roll back instead of starting over.

The two things worth backing up are:

- **Panel:** the `pelican-data` Docker volume, which holds the database and configuration
- **Wings:** the `/etc/pelican` directory, which holds the node configuration

If your server runs in a virtual machine (e.g. on Proxmox), the easiest option is to take a snapshot of the VM before updating.

### 2. Pull the new images and restart

```bash
cd ~/pelican
docker compose pull # Download the newest panel and wings images
docker compose up -d # Recreate any containers whose image changed
```

Docker Compose only recreates the containers that have a new image, so this command is safe to run even if only one of them was updated.

Once everything is running, you can delete the old images to free up disk space:

```bash
docker image prune
```

### 3. Verify the update

Check that both containers are running and watch the Panel logs for errors:

```bash
docker compose ps
docker logs --follow pelican_panel
```

Then log into the Panel, go to the "Nodes" tab, and make sure your node still has a green heart. If it shows a red heart, check the Wings logs with `docker logs --follow pelican_wings`.

If something broke, read the release notes for the version you updated to. Breaking changes and the steps to fix them are usually listed there. You can also search the [Pelican Discord server](https://pelican.dev/discord) for others who hit the same issue.
